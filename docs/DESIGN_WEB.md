# 設計書: 入口を3つ持つ1つの仕組み（MCP ホスト・Web フォーム・Web チャット）

いまの MCP サーバーを唯一の窓口にしたまま、Claude 以外の画面からも同じ集計を使えるようにする。

- 作成: 2026-10-03
- 状態: 段階A（9章）を実装済み。本番には配備するが、回数制限（7.1）が入るまで `WEB_ENABLED=false` で閉じている（11章 #1）。実装は [web/](../web/README.md) と `deploy/cloudflare/src/`
- 前提: [DESIGN.md](DESIGN.md)（全体の方式）、[deploy/cloudflare/](../deploy/cloudflare/README.md)（いまの本番）

**指標・ディメンションの定義は [CLAUDE.md](../CLAUDE.md) と `mcp_server/definitions.py` が正典。**
本書は入口の作り方だけを扱う。定義を JS やシステムプロンプトに書き写すことはしない。

---

## 1. 目的

次の3つを、**別々のアプリではなく1つの仕組み**で満たす。

| # | 入口 | 使う人 | LLM |
|---|---|---|---|
| 1 | 外部の MCP ホスト（claude.ai・Claude Desktop・ChatGPT・VS Code など） | 自分の AI を持っている人 | 利用者のもの |
| 2 | Web アプリのチャットモード | AI のアカウントを持たない人（発表会の来場者など） | こちらの Claude API |
| 3 | Web アプリのフォームモード | 条件を画面で選びたい人。誰でも | 使わない |

いまは 1 のうち claude.ai・Claude Desktop・Claude Code だけで動いている。

### 1.1 1つにまとめる理由

- **定義を二重に持たない。** 入口ごとに集計を実装すると、生活道路の strict / broad や
  年齢と当事者種別のペア判定が入口ごとにずれる。どの入口から聞いても同じ数字・同じ注記が返ること
- **ビューを作り直さない。** ダッシュボード・地図・集計表（`mcp_server/app/`）を3つの入口で共用する
- **足すときは1か所。** ツールや引数を `server.py` に足せば、3つの入口すべてに出る

### 1.2 非目的

- 定義の変更（本書は入口の話だけ）
- 全 2,182,298 件の点表示（既存 viewer + PMTiles が担当。DESIGN.md 1.3）
- 会話履歴のサーバー保存・ログイン機能

## 3. 全体構成

**Web アプリ自身を MCP ホストとして作る。** claude.ai がやっていること
（MCP サーバーに繋ぐ・ツールを呼ぶ・`ui://` のビューを iframe で描く）を自前のページでもやる。
そうすると、Web アプリは「外部ホストの1つ」と同じ立場になり、サーバー側は何も変えずに済む。

```
                       ┌──────────────── Worker（1つのデプロイ） ────────────────┐
 claude.ai         ──→ │ /s/<SECRET>/mcp ─┐                                        │
 ChatGPT / VS Code ──→ │                  ├──→ コンテナ（server.py そのまま）──→ parquet │  ← 1
                       │ /web/mcp ────────┘     ※ ツール・定義・ビューは1か所       │
 ブラウザ ─────────→   │ /          Web アプリ（静的アセット）                      │
                       │ /api/chat  Claude API の中継（API キーはここだけ）          │
                       └─────────────────────────────────────────────────────────┘

 Web アプリ（ブラウザ内）
   ├ MCP クライアント ── /web/mcp に繋ぐ（同一オリジンなので CORS 不要）
   ├ フォームモード ──── 利用者が条件を選ぶ → tools/call                     ← 3
   ├ チャットモード ──── /api/chat の Claude が tool_use を返す → tools/call ← 2
   └ ビュー描画 ──────── ui:// を iframe に読み、AppBridge で結果を渡す（両モード共通）
```

モードが違っても、`tools/call` を呼んでビューに結果を渡すところから先は同じ道を通る。
違うのは「どのツールをどの引数で呼ぶか」を誰が決めるか（利用者か Claude か）だけ。

## 4. サーバー側（Worker とコンテナ）

### 4.1 MCP サーバー: 変更しない

`mcp_server/server.py` には手を入れない。これが「1つの仕組み」の条件。

- Host / Origin 検証はコンテナ起動時に `--allow-host '*'` で外してある（`deploy/cloudflare/Dockerfile`）。
  ブラウザからの接続もそのまま通る
- セッションはコンテナのメモリ上にあり、Worker がインスタンス名を `main` に固定して
  常に同じコンテナへ送っている。Web アプリのセッションも同じ扱いで動く

### 4.2 Worker: ルートを足す

いまの `src/worker.ts` は `/s/<SECRET_PATH>/mcp` 以外を 404 にしている。これを次のように広げる。

| パス | 用途 | 守り方 |
|---|---|---|
| `/s/<SECRET_PATH>/mcp` | 外部 MCP ホスト（入口1） | いまの秘密パスのまま |
| `/web/mcp` | Web アプリの MCP クライアント（入口2・3） | 同一オリジンの Origin 検査 + 回数制限（7章） |
| `/api/chat` | Claude API の中継（入口2） | Turnstile + 回数制限 + 日額上限（7章） |
| `/`・`/assets/*` | Web アプリ本体 | なし（静的ファイル） |

**外部ホスト用と Web 用でパスを分ける。** Web アプリは URL をページに埋めるので、
同じパスを使うと秘密パスが公開されてしまう。分けておけば、Web 側を絞っても止めても
外部ホストの利用者には影響しない。

`/web/mcp` は MCP の全メソッドを素通しせず、Web アプリが使うものだけを許可する
（`initialize`・`tools/list`・`tools/call`・`resources/read`・通知）。`tools/call` は 5.3 の許可リストで絞る。

静的アセットは Workers の static assets で配る。Web アプリと API が同じオリジンになるので、
CORS の設定は要らない。

## 5. Web アプリ（自前の MCP ホスト）

### 5.1 置き場所とビルド

`web/` を新設する（TypeScript + Vite。`mcp_server/app/` と同じ道具立て）。
ビューのビルド成果物（`mcp_server/app/dist/*.html`）はコピーしない。
**ビューの HTML は実行時に `resources/read` で MCP サーバーから取る。**
claude.ai と同じ取り方にしておけば、ビューを直したときに Web 側の再ビルドが要らない。

### 5.2 ビューの描画（両モード共通）

`@modelcontextprotocol/ext-apps` の `AppBridge`（ホスト側の部品。`app-bridge` エクスポート）を使う。
いまのビューが使っている機能は次のとおりで、ホストはこれを全部まかなう必要がある。

| ビュー側の呼び出し | ホスト（Web アプリ）がやること |
|---|---|
| `ontoolinput` / `ontoolresult` / `ontoolcancelled` | `sendToolInput` / `sendToolResult` / `sendToolCancelled` で渡す |
| `callServerTool`（条件の切り替えボタン・地図の再問い合わせ） | MCP クライアントで `tools/call` して結果を返す。5.3 の許可リストを通す |
| `getHostContext` / `onhostcontextchanged` | テーマ（ライト/ダーク）・表示幅を `setHostContext` / `sendHostContextChange` で渡す |
| `requestDisplayMode`（地図の全画面） | iframe の大きさを切り替える |

iframe はサンドボックスにし、`_meta.ui.csp` で宣言されたドメインだけを CSP で許す
（地図の地理院タイル。`mcp_server/accident_map.py` の `CSP`）。
claude.ai と同じ制約で描かれるので、Web で動けば外部ホストでも動く、という確認にもなる。

### 5.3 公開するツール

| ツール | フォーム（3） | チャット（2） | 外部ホスト（1） |
|---|:-:|:-:|:-:|
| `seikatsu_dashboard` | ○ | ○ | ○ |
| `aggregate` | ○ | ○ | ○ |
| `accident_map` | ○ | ○ | ○ |
| `list_values` | （フォームの選択肢に内部で使う） | ○ | ○ |
| `run_sql` | × | × | ○ |

`run_sql` を Web に出さない理由は2つある。1つは文字コードの罠（DESIGN.md 10.2）で、
LLM が書いた SQL はエラーにならずに0件を返しうる。もう1つは、1/4 vCPU のコンテナを全員で共有しているため、
重いクエリ1本で全員が止まること（`RUN_SQL_TIMEOUT_S` = 20秒の打ち切りはあるが、その間は詰まる）。
許可リストはブラウザ側と `/web/mcp`（Worker）の両方に置き、Worker 側を正とする。

### 5.4 フォームモード（入口3）

**フォームは `tools/list` の `inputSchema` から自動で作る。** 手で画面を作り込まない。

- enum はセレクトに、配列の enum は複数選択に、整数は数値入力にする
- 各項目の説明文はスキーマの `description` をそのまま出す。strict / broad の意味のように、
  定義の説明はサーバーが持っているものを表示する
- 都道府県のように値が多いものは `list_values` で選択肢を取る
- 送信すると `tools/call` を呼び、結果を 5.2 のビューで描く。結果の注記（`notes`）もそのまま出す

これで、`server.py` に引数を足せば、フォームにも自動で項目が増える。

### 5.5 チャットモード（入口2）

**会話のループはブラウザに置き、Worker は Claude API の中継だけをする。**

```
ブラウザ ── messages + tools ──→ /api/chat ──→ Claude API
        ←── tool_use ───────────
ブラウザ ── tools/call ──→ /web/mcp ──→ コンテナ
        ←── 結果 ────────── 　→ ビューに渡して描画（5.2）
ブラウザ ── tool_result を足した messages ──→ /api/chat ──→ …（終わるまで繰り返す）
```

- **ツール定義とシステムプロンプトは MCP サーバーから取る。** `tools/list` の結果を Claude API の
  `tools` に変換し、システムプロンプトには `initialize` で返る `instructions`
  （年齢層の制約・strict / broad の明示・A/B の意味など）を使う。チャット用に定義を書き写さない
- Claude API の MCP コネクタ機能（API 側から MCP サーバーへ繋ぐ方式）は使わない。
  ツールの結果がブラウザに来ないとビューを描けないため
- 会話履歴はブラウザのメモリにだけ持つ。リロードで消える
- Worker 側でモデル名と `max_tokens` を固定し、ブラウザからは変えさせない
- ストリーミングで返す（発表会の会場で待ち時間を短く見せるため）

## 6. 外部の MCP ホスト（入口1）

サーバー側の作業は無い。いまの `/s/<SECRET_PATH>/mcp` を各ホストに登録して確かめるだけ。

| ホスト | 確かめること |
|---|---|
| claude.ai・Claude Desktop | 確認済み（#40） |
| ChatGPT | コネクタとして登録できるか、`ui://` のビューが描画されるか |
| VS Code（GitHub Copilot） | 同上 |

MCP Apps（`ui://` のビュー）は MCP の拡張仕様で、対応状況はホストごとに違う。
**描画されないホストでも `structuredContent` とテキストは返るので、集計としては壊れない**
（いま Claude Code で使っているのと同じ状態）。結果は README の対応表に残す。

## 7. 守り方と費用

### 7.1 方針

| 入口 | 何を守るか | 手段 |
|---|---|---|
| 1 外部ホスト | 公開範囲 | 秘密パス（現状維持）。組織で配るなら Cloudflare Access（DESIGN.md 11章 #2） |
| 3 フォーム | コンテナの処理能力 | `/web/mcp` に IP あたりの回数制限 |
| 2 チャット | 推論費 | Turnstile + IP あたりの回数制限 + 日額上限。上限に達したらチャットだけ止め、フォームは残す |

データは公開データの読み取りだけなので、フォームモードに認証は付けない。

### 7.2 チャットの費用

推論費はこちら持ちになる。DESIGN.md 10.3 では 1往復 約 $0.045 と見積もった
（当時のモデル・料金。実装時に使うモデルで計り直す）。

- 上限は2段にする。1人あたりは Worker の回数制限で、全体は日額上限で抑える
- 日額上限は Worker 側で数える（Durable Object か KV）。API キー側の利用上限も併せて設定する
- 発表会の期間だけチャットを開け、終わったら閉じられるようにする（#31 の一時 URL と同じ考え方）

## 8. 同時利用と性能

3つの入口が、`max_instances: 1`・basic（1/4 vCPU・1 GiB）のコンテナ1台を共有する。

- 2025年版での実測（#40）は、起きている状態で dashboard 1.0〜1.6 秒・map 2.7〜3.9 秒。
  40人が同時に地図を開くと、単純計算で後ろの人は2分以上待つことになる
- `max_instances` を増やすと、セッションがコンテナのメモリにあるため、インスタンス名の振り分けを
  変える必要がある（4.1）
- 判断は #32（負荷試験）で行う。負荷のかけ方には Web アプリ経由の利用も含める

|---|---|---|
| A | Worker のルート追加（4.2）と Web アプリの土台（MCP クライアント + 5.2 のビュー描画） | 固定の引数で `seikatsu_dashboard` を呼び、ダッシュボードが描ける |
