# 設計書: 交通事故統計 集計・可視化基盤

警察庁交通事故統計オープンデータの変換済みデータ（GeoParquet）を Cloudflare R2 に配置し、
ブラウザ上で任意の切り口の集計を実行・閲覧できるようにする。

- 作成日: 2026-09-14
- 対象データ: 2019〜2024年（本票）1,895,275件
- 前段リポジトリ: [npa-traffic-accident-converter](../../npa-traffic-accident-converter)

---

## 1. 背景と目的

### 1.1 現状の課題

変換済みデータは CSV・GeoParquet・PMTiles として公開されているが、集計は利用者が
手元にデータをダウンロードして Python なり SQL なりを書く必要がある。

- 単年CSVは1ファイル 217〜281MB、マージ済みCSVは 1.4GB
- 「生活道路の若年層の事故は増えているのか」といった問いに答えるまでの手数が多い
- 地図ビューアは個票を地図上で見るもので、集計値を見るものではない

### 1.2 目的

条件を指定して集計結果（経年推移・構成比・クロス集計）をブラウザ上で即座に得られるようにする。
サーバ側にデータベースやAPIを持たず、静的ファイル配信のみで完結させる。

### 1.3 非目的

- 個票を地図上に表示すること（既存の viewer と PMTiles が担当）
- 補充票・高速票の集計（本票のみを対象とする）
- 統計的推論・予測（記述統計のみ）

## 2. 方式決定

### 2.1 採用方式

**Cloudflare R2 に置いた Parquet を、ブラウザ内の DuckDB-WASM が HTTP Range リクエストで
部分取得しながら集計する。**

サーバ側の計算資源を一切使わない。

### 2.2 根拠となる実測値

Parquet は列指向かつ row group 単位で統計を持つため、クエリに必要な列・行群だけを
Range リクエストで取得できる。実際に Range 対応の HTTP サーバ経由で計測した。

| クエリ | ファイル全体 | 実転送量 | リクエスト数 | 所要時間 |
|---|---:|---:|---:|---:|
| 生活道路×若年層、全6年の集計 | 96.6 MB | **4.07 MB (4.2%)** | 62 | 0.91秒 |
| 同、2024年のみに絞る | 96.6 MB | **0.84 MB (0.9%)** | 20 | 0.05秒 |

集計に使う列は小さい。全1,895,275行を通しての圧縮後サイズは以下のとおり。

| 列 | 圧縮後 |
|---|---:|
| 車道幅員 | 0.95 MB |
| 年齢（当事者A / B） | 1.42 MB |
| 当事者種別（当事者A / B） | 2.21 MB |
| 事故内容 | 0.04 MB |
| 都道府県名 | 0.01 MB |

一方、座標系の4列 + geometry で 89.8 MB（元ファイルの73%）を占めるが、
集計クエリではこれらの列を読まないため転送されない。

### 2.3 検討した他方式

| 方式 | 集計場所 | 月額 | 任意集計 | 不採用の理由 |
|---|---|---:|---|---|
| 事前集計 JSON | GitHub Actions | 0円 | × | 切り口を事前に決め打つ必要がある |
| Workers + R2 | サーバレス | 数百円〜 | ○ | この規模ではブラウザ内で足りる。運用が増える |
| BigQuery + Looker | GCP | 従量 | ○ | データがGCPに移る。コストが利用量に比例する |

将来データ量が数十倍になる、あるいは重い空間結合が必要になった場合は
Workers + R2 への移行を検討する。その際も R2 上のファイルはそのまま使える。

### 2.4 コスト

Cloudflare R2 の無料枠内に収まる。

- ストレージ: 96.6 MB（無料枠 10 GB/月）
- egress: 無料（R2 の特徴）
- Class B オペレーション（読み取り）: 1クエリあたり20〜62リクエスト（無料枠 1,000万回/月）

月10万クエリ実行しても無料枠に収まる規模。

## 4. データ層

### 4.1 入力

前段リポジトリが生成する `output/honhyo_2019-2024_converted.parquet`。
GeoParquet 1.0.0、Snappy圧縮、1,895,275行 × 72列 + geometry、128.1 MB。

### 4.2 加工内容

| 項目 | 入力 | 出力 | 理由 |
|---|---|---|---|
| 資料年次列 | なし | int16 で追加 | 後述 4.3 |
| 圧縮 | Snappy | zstd-9 | 128.1 MB → 96.6 MB（25%削減） |
| row group | 2個（各1,048,576行） | 15個（各131,072行） | 年・条件での row group プルーニングを効かせる |
| 行の並び | ファイル年次順 | 変更なし | すでに資料年次でソート済みの状態になる |
| GeoParquet メタデータ | あり | 保持 | geopandas / QGIS から引き続き読めるようにする |

列の削除は行わない。座標列は集計時に読まれないため、残しても転送量に影響しない（2.2 参照）。
1ファイルで地図用途と集計用途の両方を賄う。

### 4.3 年次基準を2系統持つ

本データには「年」の意味が2つある。**両方を列として保持し、UI 側で選択させる。**

警察庁の年次ファイルには、前年末に発生して当年に計上された事故が毎年8,000〜9,000件含まれる。

縦＝発生年、横＝どの年のファイルに入っていたか（実測）:

| 発生年＼ファイル | 2019 | 2020 | 2021 | 2022 | 2023 | 2024 | 発生年 合計 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 2018以前 | 10,394 | 53 | 11 | 3 | 1 | 0 | 10,462 |
| 2019 | 370,843 | 9,321 | 28 | 5 | 2 | 1 | 380,200 |
| 2020 | | 299,804 | 8,069 | 28 | 5 | 1 | 307,907 |
| 2021 | | | 297,088 | 8,380 | 32 | 3 | 305,503 |
| 2022 | | | | 292,423 | 9,071 | 37 | 301,531 |
| 2023 | | | | | 298,819 | 8,477 | 307,296 |
| 2024 | | | | | | 282,376 | **282,376** |
| **ファイル合計** | **381,237** | **309,178** | **305,196** | **300,839** | **307,930** | **290,895** | |

| | 資料年次（計上年） | 発生日時_年（発生年） |
|---|---|---|
| 列 | `資料年次` int16（本リポジトリで付与） | `発生日時_年`（converter が出力済み） |
| 公表値との一致 | **一致する**（381,237 / 309,178 / … は警察庁公表の発生件数そのもの） | 一致しない |
| 最新年の完全性 | 確定済み | **約3%過少**。翌年ファイルで追加される |
| 事故の発生時点 | 最大1年ずれる | 正確 |
| 月次・季節性分析 | 不可 | 可能 |

**既定値は `資料年次`**。公表値と照合でき、最新年が過少に出ないため。
経年推移グラフで発生年基準を使うと、最新年だけが見かけ上3%低く描画され、
実際の減少と区別がつかなくなる。

月次推移・季節性を見る場合のみ `発生日時_年` + `発生日時_月` を使う。

### 4.4 出力仕様

```
honhyo_2019-2024.parquet
  形式        : Parquet (GeoParquet 1.0.0 準拠)
  圧縮        : zstd level 9
  row group   : 131,072行 × 15
  行数        : 1,895,275
  列数        : 73 + geometry
  サイズ      : 96.6 MB
  並び順      : 資料年次 昇順
```

型は converter の出力に準じて原則 string のままとする。
`資料年次` のみ int16。数値集計が必要な `死者数` `負傷者数` は
クエリ側で `CAST` する（列サイズが小さく、キャストコストは無視できる）。

### 4.5 更新フロー

新年次（2025年）追加時:

1. converter 側で `python -m converter --all --merge` → `./export_geo.sh`
2. 本リポジトリの `pipeline/build_parquet.py` を実行
3. R2 へアップロード
4. app 側の年次リストとキャッシュキーを更新

年1回の更新であり自動化の優先度は低い。手順を `docs/OPERATIONS.md` に記載する。

## 5. 配信層（Cloudflare R2）

### 5.1 バケット構成

```
npa-traffic-accident-data/
├── honhyo_2019-2024.parquet
└── honhyo_2019-2024.pmtiles      # 既存 xserver から移設（任意）
```

### 5.2 必須設定

**カスタムドメインを使用する。** `r2.dev` の公開URLはレート制限があり本番利用が想定されていない。

CORS 設定（DuckDB-WASM / PMTiles の双方に必要）:

```json
[
  {
    "AllowedOrigins": ["https://shiwaku.github.io"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["range", "if-match"],
    "ExposeHeaders": ["content-range", "content-length", "etag", "accept-ranges"],
    "MaxAgeSeconds": 3600
  }
]
```

`ExposeHeaders` に `content-range` が無いと、DuckDB-WASM が部分取得の結果を
正しく解釈できずファイル全体を読みにいく。ここは動作確認項目とする。

### 5.3 キャッシュ

ファイルは年1回しか更新されないため、Cache-Control を長く取る。
更新時はファイル名にバージョンを含めて別オブジェクトとして置き、
app 側の参照先を切り替える（キャッシュパージ不要）。

```
Cache-Control: public, max-age=31536000, immutable
```

## 6. 集計層（DuckDB-WASM）

### 6.1 初期化

```ts
const db = await duckdb.createDuckDB(...)   // @duckdb/duckdb-wasm
await db.instantiate(...)
const con = await db.connect()
await con.query(`INSTALL httpfs; LOAD httpfs;`)
await con.query(`
  CREATE VIEW honhyo AS
  SELECT * FROM read_parquet('${PARQUET_URL}')
`)
```

バンドルは COI（Cross-Origin Isolation）不要の非 multithread 版を既定とする。
GitHub Pages では COOP/COEP ヘッダを設定できないため。
実測 0.91秒 はシングルスレッドでの値であり、これで十分実用に足る。

### 6.2 クエリの形

UI のフィルタ状態から SQL を組み立てる。基本形:

```sql
SELECT
  資料年次 AS 年,
  count(*) AS 件数,
  sum(CAST(死者数 AS INTEGER))   AS 死者数,
  sum(CAST(負傷者数 AS INTEGER)) AS 負傷者数
FROM honhyo
WHERE 1=1
  {道路条件}
  {当事者条件}
  {地域条件}
GROUP BY 1
ORDER BY 1
```

当事者条件は A/B の2列に跨るため、条件式を組み立てる際に注意が必要（8.3 参照）。

### 6.3 性能目標

| 操作 | 目標 |
|---|---|
| 初回ロード（DuckDB-WASM 初期化 + フッタ読み込み） | 3秒以内 |
| フィルタ変更後の再集計 | 1秒以内 |
| 年を絞った集計 | 0.3秒以内 |

実測（ローカル Range サーバ）で全6年 0.91秒、単年 0.05秒。R2 の RTT が加わるが目標内に収まる見込み。

### 6.4 キャッシュ戦略

同一条件の再実行を避けるため、組み立てた SQL 文字列をキーにクエリ結果をメモリ上に保持する。
DuckDB 側も一度読んだ row group をバッファプールに保持するため、
2回目以降のフィルタ変更は転送を伴わないことが多い。

| 指標 | 定義 |

## 8. 指標・ディメンションの定義

集計結果の意味を決める定義。UI 上でも定義を明示する。

### 8.1 生活道路

警察庁の統計上の生活道路は「車道幅員5.5m未満の道路」。
`車道幅員` 列は単路と交差点で意味が異なる（交差点は交差する2道路の幅員の組み合わせ）。

| コード | ラベル | 5.5m未満の扱い |
|---|---|---|
| 01 | 単路－3.5m未満 | 該当 |
| 02 | 単路－3.5m以上（3.5〜5.5m） | 該当 |
| 03〜06 | 単路－5.5m以上 ほか | 非該当 |
| 11 | 交差点－小（5.5m未満）－小 | 該当（両道路が5.5m未満） |
| 14 / 17 | 交差点－中－小 / 大－小 | **一方のみ5.5m未満** |
| 15 / 18 / 19 | 交差点－中－中 ほか | 非該当 |
| 00 | 一般交通の場所 | 幅員不明 |

**既定は厳密定義（01, 02, 11）。** 2024年で45,296件（全体の15.6%）。

14（中－小）だけで44,733件あり、これを含めるかで結果が約2倍変わる。
生活道路から幹線に出る出会い頭事故はここに含まれるため、UI では
「厳密 / 広義（片側のみ5.5m未満を含む）」を切り替えられるようにする。

### 8.2 若年層

`年齢` 列は実年齢ではなく**年齢層コード**である
（`0～24歳 / 25～34 / 35～44 / 45～54 / 55～64 / 65～74 / 75歳以上 / 不明`）。

したがって「若年層」として取り出せるのは **`0～24歳` の1区分のみ**。
未就学児・小学生・高校生・大学生・若手社会人がすべて同じ区分に入り、
「10代のみ」「未成年のみ」といった切り出しは**原理的に不可能**。

この制約は UI 上に明示する。年齢に関する解釈を誤らせないため。

### 8.3 当事者A / B

- **当事者A = 第1当事者 = 過失が最も重い側**
- **当事者B = その相手方**

被害者かどうかで決まる区分ではない。ただし実態としては大半が被害側（2024年実測）:

| | 損傷なし | 負傷 | 死亡 | 対象外 |
|---|---:|---:|---:|---:|
| 当事者A | 228,943 | 61,215 | 714 | 23 |
| 当事者B | 48,874 | 223,617 | 1,687 | 16,717 |

Bが死傷しているのは77.5%。一方でBが無傷の事故も48,874件（16.8%）、
Aが死傷した事故も61,929件（21.3%）ある。

集計の対象として以下を選べるようにする:

| 選択 | 意味 |
|---|---|
| A | 過失が重い側が該当条件 |
| B | 相手方が該当条件 |
| A または B | 該当者が関与した事故（**重複カウントしない**） |

**年齢と当事者種別は同一当事者でペア判定する必要がある。**
「年齢Aが0～24歳」かつ「当事者種別Bが歩行者」という組み合わせで
マッチさせてしまうと別人の属性を掛け合わせることになる。

```sql
-- 正しい
(年齢（当事者A）='0～24歳' AND 当事者種別（当事者A） IN (...))
OR (年齢（当事者B）='0～24歳' AND 当事者種別（当事者B） IN (...))
```

また A・B の双方が条件に合致する事故（若年自転車同士の事故など、2019年で58件）を
二重に数えないよう `count(*) FILTER (...)` で行単位に数える。

### 8.4 自転車

`軽車両－自転車` に加え `軽車両－駆動補助機付自転車`（電動アシスト）を含める。
`特定小型原付自転車`（電動キックボード等、2024年〜）は**含めない**。別区分として扱う。

## 9. 非機能要件

| 項目 | 要件 |
|---|---|
| 対応ブラウザ | Chrome / Edge / Firefox / Safari の各最新2バージョン |
| モバイル | 閲覧可能（フィルタは折りたたみ）。ただし数MBの転送が発生する旨を表示 |

## 12. 既知の制約

前段リポジトリから引き継ぐもの、およびデータ自体に由来するもの。

1. **年齢は7区分の年齢層のみ**。実年齢は取得できない（8.2）
2. **本票は人身事故のみ**。物損事故は含まれない
3. **2019〜2021年の警察署等・高速路線コード**は2019年版のみが提供されており、
   2020・2021年に新設された署・路線は未収録。該当レコードは空欄
4. **2024年のトンネル番号**は2023年版CSVを使用しており、10件程度が不正確な可能性
5. **2019〜2021年は72列のうち12列が存在しない**（日の出入時刻・オートマチック車・
   サポカー・認知機能検査経過日数・運転練習の方法）。出力上は空値
6. **自転車が第1当事者と判定される割合が2022年に不連続に変化している**。
   生活道路上の自転車で18.3%（2019）→28.2%（2024）、2021→2022 で 21.8%→26.6% と段差がある。
   事故実態の変化か過失認定の運用変更かは判別できない。
   A/B 別の時系列比較を行う際は注意を要する。UI 上に注記を出す
