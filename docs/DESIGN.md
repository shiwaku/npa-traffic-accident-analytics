# 設計書: 交通事故統計 集計・可視化基盤

警察庁交通事故統計オープンデータを Cloudflare R2 上の GeoParquet として公開し、
Claude Code との対話で集計・可視化する。

- 作成: 2026-09-14
- 対象: 2019〜2024年（本票）1,895,275件
- 前段: [npa-traffic-accident-converter](../../npa-traffic-accident-converter)

**指標・ディメンションの定義は [CLAUDE.md](../CLAUDE.md) が正典。**
本書はシステム構成を扱い、定義は重複させない（二重管理は必ず乖離する）。

---

## 1. 背景と目的

### 1.1 課題

変換済みデータは CSV・GeoParquet・PMTiles として公開済みだが、集計には
手元にダウンロードして Python や SQL を書く必要がある。

- 単年CSV 217〜281MB、マージ済みCSV 1.4GB
- 「生活道路の若年層の事故は増えているのか」に答えるまでの手数が多い
- 地図ビューアは個票を見るもので、集計値を見るものではない

### 1.2 目的

条件を自然言語で伝えるだけで集計結果が得られ、表・グラフ・地図で確認できるようにする。
サーバ・データベース・APIを持たない。

### 1.3 非目的

- 一般公開ダッシュボード（後述 10.2 のとおり意図的に採らない）
- 個票の地図表示（既存 viewer + PMTiles が担当）
- 補充票・高速票（本票のみ）
- 統計的推論・予測（記述統計のみ）

---

## 2. 方式

**R2 に置いた Parquet を、Claude Code セッションからローカルの DuckDB が
HTTP Range で部分取得しながら集計する。** 自然言語の解釈はモデルが直接担う。

```
利用者「生活道路の若年層の事故件数の経年推移」
   ↓
Claude Code  ── CLAUDE.md の定義を読んで SQL を組み立てる
   ↓
DuckDB + httpfs
   ↓ HTTP Range（必要な列だけ、約4MB）
Cloudflare R2 / shi-works.com
   ↓
集計結果 → 表（ターミナル）/ グラフ・地図（Artifact）
```

構築物は **R2 上のファイル1つと CLAUDE.md** のみ。アプリケーションコードは無い。

### 2.1 なぜ成立するか

Parquet は列指向かつ row group 単位で統計を持つため、必要な列・行群だけを
Range リクエストで取得できる。96.6MB のうち集計に使う列は 4.6MB 程度しかない。

| 列 | 圧縮後 |
|---|---:|
| 車道幅員 | 0.95 MB |
| 年齢（当事者A / B） | 1.42 MB |
| 当事者種別（当事者A / B） | 2.21 MB |
| 事故内容 | 0.04 MB |
| 都道府県名 | 0.01 MB |

座標系の列（geometry・緯度経度4列）が 89.8 MB（全体の73%）を占めるが、
集計では読まれないため転送されない。列を削って軽量版を作る必要はない。

## 3. データ層

### 3.1 R2 上の仕様

```
URL   : https://shi-works.com/geoparquet/npa-traffic-accident-analytics/honhyo_2019-2024.parquet
形式  : Parquet (GeoParquet 1.0.0 準拠、EPSG:4326)
圧縮  : zstd level 9
rowgrp: 131,072行 × 15
行数  : 1,895,275
列数  : 73 + geometry
サイズ: 96,553,319 bytes (96.6 MB)
並び  : 資料年次 昇順
ETag  : "0f60d955391376abef42f7e6668bd757-12"
```

Content-Type は `application/vnd.apache.parquet`、
Cache-Control は `public, max-age=31536000, immutable`。

ファイル名に年次範囲を含めるため、2025年追加時は `honhyo_2019-2025.parquet` という
別キーになる。immutable キャッシュのまま安全に増やせ、パージが要らない。

### 3.2 前段出力からの加工

| 項目 | 前段出力 | R2配信用 | 理由 |
|---|---|---|---|
| `資料年次` 列 | なし | int16 で追加 | 3.3 |
| 圧縮 | Snappy | zstd-9 | 128.1 → 96.6 MB |
| row group | 2個（各1,048,576行） | 15個（各131,072行） | 年での読み飛ばしを効かせる |
| 列の削除 | — | 行わない | 集計時に読まれないため不要（2.1） |
| GeoParquet メタデータ | あり | 保持 | geopandas / QGIS から引き続き読める |

`pipeline/build_parquet.py` が担当。1.9M行の再変換は行わず、
マージ済み parquet に列を足して書き直すだけ（実測11秒）。

行の対応付けは位置ベース。マージが年次順の concat であり座標欠損による行落ちも
無いため、単年CSVの行数を積み上げた区間が各年のブロックになる。
`--verify` で本票番号・都道府県名まで全6年を照合できる（照合済み）。

### 3.3 年次基準を2系統持つ

年次ファイルには前年末に発生して当年に計上された事故が毎年8,000〜9,000件含まれる。
`資料年次`（計上年）と `発生日時_年`（発生年）の両方を列として保持し、用途で使い分ける。

既定は `資料年次`。ファイル合計が警察庁公表の発生件数と一致し、最新年が過少に出ない。
クロス集計表と判断基準は [CLAUDE.md](../CLAUDE.md#年次基準) を参照。

## 4. 配信層（Cloudflare R2）

### 4.1 構成

既存資産をそのまま使う。新規に作る設定は無かった。

| 項目 | 状態 |
|---|---|
| バケット | `shi-works`（既存） |
| カスタムドメイン | `shi-works.com`（設置済み） |
| プレフィックス慣習 | `<形式>/<リポジトリ名>/<ファイル名>` |
| 認証 | ローカル aws プロファイル `r2-shiworks`、GitHub Actions は `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` |

### 4.2 検証済みの配信特性

| 項目 | 実測 |
|---|---|
| Range リクエスト | `206 Partial Content` / `Content-Range` 正常 |
| `Accept-Ranges` | `bytes` |
| CORS | `Access-Control-Allow-Origin: *` |
| `Access-Control-Expose-Headers` | `ETag, Content-Range, Accept-Ranges, Content-Length, Content-Encoding` |

`Expose-Headers` に `Content-Range` が含まれるため、将来ブラウザ内 DuckDB-WASM で
読む選択肢もそのまま残っている（10.1 参照）。

### 4.3 コスト

R2 無料枠内。ストレージ 96.6MB（枠10GB）、egress 無料、
読み取り Class B は1クエリ20〜62リクエスト（枠1,000万回/月）。

## 5. 分析層（DuckDB）

### 5.1 接続

```python
import duckdb
URL = 'https://shi-works.com/geoparquet/npa-traffic-accident-analytics/honhyo_2019-2024.parquet'
con = duckdb.connect()
con.execute("INSTALL httpfs; LOAD httpfs;")
con.execute(f"CREATE VIEW honhyo AS SELECT * FROM read_parquet('{URL}')")
```

利用可能な拡張（動作確認済み）: `httpfs` / `spatial` / `h3`（community）。

### 5.2 実測性能

| 操作 | ローカルRange | R2経由 |
|---|---:|---:|
| ビュー作成（フッタ読み込み） | — | 1.33秒 |
| 生活道路×若年層、全6年 | 0.91秒 / 4.07MB / 62req | 2.05秒 |
| 同、2024年のみ | 0.05秒 / 0.84MB / 20req | — |

R2 経由でもローカル集計と結果が完全一致することを確認済み。
差は RTT 分のみで、対話のテンポを損なわない。

年で絞ると転送量が1/5になるのは、資料年次で行が整列しており
row group 統計によるプルーニングが効くため。

## 6. 閲覧層

### 6.1 表

ターミナルに Markdown 表で出す。実数に加えて指数（基準年=100）と構成比を併記する。
2020年はコロナ禍で全体件数が前年比19%減しており、実数だけでは傾向を読み誤る。

### 6.2 グラフ・地図（Artifact）

**制約: Artifact として公開したページは外部へのfetch/XHRがCSPで全てブロックされる。**
R2 からデータを取得できず、地図タイルも読めない。したがって公開ページは
**集計結果を埋め込んだ自己完結のスナップショット**になる。

| 用途 | 埋め込みサイズ | 可否 |
|---|---:|---|
| 集計表・経年推移グラフ | 数KB | ○ |
| 都道府県別コロプレス（境界込み） | 307 KB | ○ |
| 絞り込んだ点データ（例: 8,300件） | 約150 KB | ○ |
| 全1,895,275件の点表示 | 数十MB | ×（既存 viewer + PMTiles） |

都道府県境界は `../archive/npa-accident-hotspot-analyzer/input/prefecture.parquet`
（47件、EPSG:6668）。離島込みで121,990ポリゴン・21.6MBあるが、
小ポリゴンを落として単純化すると115ポリゴン・307KBになる。
`simplify` だけでは離島が残って縮まない点に注意。

背景地図タイルは読めないが、集計地図なら境界ポリゴン自体が背景として機能する。

## 10. 検討して採らなかった方式

### 10.1 ブラウザ内 DuckDB-WASM + フィルタUI

R2 の Parquet をブラウザ内の DuckDB-WASM が読み、フィルタUIで条件を指定する構成。
技術的には成立する（CORS の `Expose-Headers` も設定済みで、そのまま動く）。

採らなかったのは、**対話の相手が既にいるのに UI を作る必要が無いため**。
フィルタUIは事前に決めた軸しか操作できず、「生活道路の厳密/広義」のような
解釈の分岐を扱えない。実装量に対して得られるものが少ない。

### 10.2 自然言語クエリ機能付きWebアプリ

Cloudflare Worker が Claude API を呼び、質問文をフィルタ仕様のJSONに変換して
ブラウザ内の DuckDB-WASM が実行する構成。1クエリ約$0.01。

一般公開が要件になれば有効だが、現時点では過剰。加えて、
**この構成でも意味論の定義（CLAUDE.md の内容）をシステムプロンプトとして
用意する必要がある**ため、いま CLAUDE.md を書いておくことは無駄にならない。

なお、その構成ではLLMに生SQLを書かせてはいけない。コード表のラベルは
全角ハイフンマイナス U+FF0D と全角チルダ U+FF5E を使っており、
似た別文字を1つ混ぜるとエラーにならず0件が返る。enum で制約した
構造化出力にし、コード値からラベルへの変換はアプリ側の辞書で行う必要がある。

### 10.3 事前集計 JSON / BigQuery + Looker

前者は切り口を事前に決め打つ必要があり、後者はデータがGCPに移りコストが
利用量に比例する。いずれもこの規模・用途には合わない。

### 10.4 geospatial-kiro-power-pack（AWS）

19個のMCPサーバーを束ねた地理空間ツール群。Kiro IDE 向けであること、
価値の中心が「断片化した外部データソースの統一アクセス」にあり
単一ファイルを扱う本件と噛み合わないこと、空間SQL部分は手元の DuckDB で
既に動くことから採らない。

OSM・標高・気象などで事故データを補強する段階に進むなら、
19個まとめてではなく `geo-vector` 単体の導入を検討する。
