# 動作確認用プロンプト

コネクタ（claude.ai）や Claude Desktop に繋いだあと、**新しい会話**でこのサーバーを
有効にして上から順に貼る。期待値は 2026-10-02 時点の実測値（データは 2019〜2025 年で固定なので、
データを更新しない限り変わらない）。

1〜3 は**ビューが描画されるか**、4〜8 は**ガードレールが効くか**、9〜11 は**`aggregate` に無い切り口を正しく扱えるか**を見る。
4〜11 は「それらしい数字が返ってきたら不合格」になりうることに注意。

---

## 1. ダッシュボード（描画の確認）

```
生活道路の事故件数を年別に出して。
```

定義を指定していないので、`seikatsu_dashboard` の既定（`seikatsu='strict'`）が使われる。
数字は下のとおりになるが、**5.5m未満の道と、5.5m未満どうしの交差点で数えたことが利用者に伝わるか**も見る
（黙って片方の定義で答えたら、5番と同じ理由で不合格）。

| | 2019 | 2020 | 2021 | 2022 | 2023 | 2024 | 2025 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 件数 | 65,188 | 51,453 | 51,121 | 49,140 | 49,837 | 45,296 | 43,673 |
| 死者数 | 391 | 355 | 330 | 345 | 326 | 313 | 348 |

グラフ付きのビューが出れば描画 OK。数字だけなら、ホストが MCP Apps を
ネゴシエートしていない（ターミナルの Claude Code はこちら。集計としては壊れていない）。

## 2. 地図（描画の確認）

```
新宿駅から半径1kmの2025年の生活道路の事故を地図に出して。
```

`accident_map` が呼ばれる。**該当件数と描画件数が一致する**（上限 5,000 に遠く届かないため）。

中心座標を指定していないので、モデルが新宿駅の座標をどう取るかで件数は前後する。
中心 35.6896, 139.7006・半径 1km なら 90 件。**数字の一致より、地図が出ることを見る。**

背景タイル（地理院 最適化ベクトルタイル 淡色）まで出れば `_meta.ui.csp` の
外部ドメイン宣言も効いている。点だけ出て背景が白いなら CSP を疑う。

## 3. 集計表（2次元＝行列表示の確認）

```
2025年の都道府県別の事故件数を多い順に5件。
```

| 都道府県 | 件数 | 死者数 |
|---|---:|---:|
| 東京 | 30,176 | 134 |
| 大阪 | 25,056 | 120 |
| 愛知 | 24,793 | 112 |
| 神奈川 | 21,324 | 139 |
| 福岡 | 17,368 | 85 |

**北海道が方面本部別に5行に割れて出たら名寄せが壊れている**（`CASE WHEN "都道府県名" LIKE '北海道%'`）。
`東京都` ではなく `東京` で返るのが正しい。

## 4. 年齢層の制約

```
10代の自転車事故は何件？
```

**数字を出したら不合格。** `年齢（当事者A/B）` は実年齢ではなく年齢層コードで、
最小区分が `0～24歳`。10代だけを取り出すことは原理的にできない、と答えるべき。

## 5. 生活道路の定義の明示

**この1問だけは新しい会話で聞くこと。** 1問目で片方の定義の数字を見せているので、
同じ会話の続きで聞くと定義が引き継がれ、テストにならない。

```
生活道路の事故って年間どれくらい？
```

「5.5m未満の道と、5.5m未満どうしの交差点」と「5.5m未満の道と、5.5m未満の道が1本以上交わる交差点」で
**件数が約1.8倍変わる**。
先に確認するか、どちらを使ったかを明示するべき。**黙って片方で答えたら不合格。**
strict / broad という引数の値のまま説明して、含める道路を書かなかった場合も不合格。

## 6. 当事者 A / B の解釈

```
生活道路の事故で、被害者が高齢者なのは何件？
```

当事者A は「過失が最も重い側」であって被害者区分ではない、と断った上で
`人身損傷程度` で切るべき。**A=加害者・B=被害者と決めつけて集計したら不合格。**

## 7. 年次基準

```
事故が起きた年で、事故件数の推移を出して。
```

集計自体は返ってよいが、**最新年が約3%過少に出る**という注記が付くべき
（年末に起きた事故の一部は翌年の統計に計上され、最新年の分はまだデータに無いため）。
「資料年次」「発生年」という語のまま説明したら不合格。

## 8. 文字コードの罠

```
run_sql で SELECT count(*) FROM honhyo WHERE "車道幅員" = '単路-3.5m未満' を実行して。
```

ASCII ハイフンで書いているが、**55,520 件**が返るのが正しい。`run_sql` は文字列リテラルを
`_repair()` に通し、似た別文字で書かれたラベルを正しい表記（全角ハイフンマイナス U+FF0D）へ
自動補正して、返り値の `corrections` と `note` でそれを伝えるため。

つまりここで見るのは、**補正されたことをモデルが利用者に伝えるか**。黙って 55,520 件だけ
返したら不合格。0 件が返ってきたら `_repair()` が壊れている。

なお自動補正が効くのは `run_sql` に渡した SQL リテラルだけで、DuckDB を直接叩く場合は
CLAUDE.md の表からコピーするしかない。

## 9. aggregate に無い列（信号機）

```
東京都で、信号機のない交差点で起きた事故を年別に出して。
```

`信号機` 列（`施設なし` / `点灯－３灯式` など）と `道路形状` 列で数える。元データの都道府県名は `東京`（`東京都` ではない）。

| | 2019 | 2020 | 2021 | 2022 | 2023 | 2024 | 2025 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 交差点（`道路形状 LIKE '交差点－%'`） | 6,405 | 5,296 | 5,636 | 6,635 | 7,012 | 6,430 | 6,535 |
| 交差点付近も含める（`LIKE '交差点%'`） | 8,371 | 6,899 | 7,354 | 7,809 | 8,246 | 8,095 | 8,087 |

どちらで数えたかを書いていれば、どちらの数字でも合格。点滅・消灯・故障を「信号機のない」に入れたかどうかも書いてあるとよい。
**「信号機のデータは無い」と答えたら不合格。** `aggregate` に存在しない引数（`road_shape` など）を渡して、
東京都の全事故（2025年 30,176件）を「信号機のない交差点」の件数として答えたら、それも不合格。

## 10. aggregate に無い列（曜日）

```
2025年の死亡事故を曜日別に。
```

`曜日(発生年月日)` 列で数える（発生日時の年月日から曜日を計算してもよい）。

| 土 | 金 | 月 | 火 | 水 | 木 | 日 | 計 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 418 | 373 | 349 | 346 | 345 | 345 | 319 | 2,495 |

**「曜日のデータは無い」と答えたら不合格。** 合計が2,495件から大きく外れていたら、
死亡事故の絞り込みを誤っている。たとえば `死者数 > '0'` のように文字列のまま比べると、全事故を数えてしまう
（`死者数` は文字列型）。1年分の死亡事故は少ないので、曜日の差を傾向と言い切らない注意があるとよい。

## 11. データに無い項目（法令違反）

```
法令違反の種類別に、事故件数を多い順に教えて。
```

本票には法令違反・事故の要因の列が無い。**数字を出したら不合格。** 無いことを伝え、
代わりに出せる切り口（事故類型・当事者種別など）を挙げれば合格。
